# AGENTS.md

Context for AI coding agents working in this repository. Read this before writing code.

## What this is

Tessera is a tick-based, tile-grid multiplayer game in Go. Three binaries — `auth`,
`world`, `client` — plus `shared` for anything more than one of them imports.

It is a proof of concept for **multiple world servers sharing one player database**. Most
of the non-obvious design below exists to make that safe. Don't simplify it away.

## Layout

```
auth/     authentication, account creation, world list
world/    world server — tick loop, game state, connections
client/   Ebitengine game client
shared/   protocol, game data types, anything imported by more than one binary
data/     map chunks, item and monster definitions (JSON)
```

Protocol types live in `shared` and are imported by both server and client. Never define a
message type in two places.

## Rules that are load-bearing

Breaking these produces bugs that are expensive to find. If a change appears to require
breaking one, stop and raise it rather than working around it.

1. **The tick goroutine owns all game state.** Connection goroutines decode intents onto a
   channel and write from another. Nothing else reads or mutates world state. Do not add
   a mutex to game state — if you feel you need one, the access is in the wrong goroutine.

2. **Every timer is a tick count, never wall-clock.** Cooldowns, respawns, despawn timers,
   lease expiry in tests. No `time.Now()`, `time.Since` or `time.Sleep` in game logic.
   This is what makes the simulation deterministic.

3. **The server is authoritative.** The client sends intents and renders. It is never
   trusted about position, damage, inventory or identity. Player identity comes from the
   verified token, never from a field in a packet.

4. **Dependencies are interfaces, injected from `services.go`.** No globals, no
   singletons, no package-level state. Interfaces are defined in the package that
   *consumes* them, not beside their implementation.

5. **Postgres holds only mutable data.** Items, monsters, loot tables and the map are JSON
   loaded at boot. Adding a table for static game data is wrong.

6. **A player exists on exactly one world.** Ownership is a database claim with a lease.
   Never bypass `ClaimStore` to read or write a player row that another world may hold.

## Injected services

Each has a production and a test implementation. Use the interface, never construct the
concrete type outside `services.go`.

| Interface | Production | Test |
|---|---|---|
| `Clock` | ticker at 600ms | manual step |
| `RandSource` | seeded at startup | fixed seed |
| `Codec` | msgpack | recording spy |
| `MessageSink` | channel to writer goroutine | slice recorder |
| `PlayerStore` | sqlc + pgx | in-memory map |
| `ClaimStore` | sqlc + pgx | in-memory map |
| `GameData` | JSON loader | fixtures |

Introduce a new interface only when a second implementation exists or is imminent. Pure
functions over data — pathfinding, inventory stacking, combat maths — are called directly
and tested directly. Don't wrap them.

## Stack

- **Transport:** WebSocket (`coder/websocket`), binary frames
- **Encoding:** msgpack, short struct tags, behind the `Codec` interface
- **Database:** PostgreSQL via pgx; queries generated by **sqlc**; migrations by **goose**
- **Client:** Ebitengine
- **Map authoring:** Tiled, converted to chunk files at build time

Do not add an ORM. Do not add a DI framework — wiring is explicit in `services.go`.

## Database changes

1. Write a goose migration in `migrations/`. Both up and down must run clean.
2. Update or add the query in the sqlc query files.
3. Run `make generate`.
4. Commit the generated code.

sqlc reads the migrations directory as its schema, so a migration and its queries must
land together. Never hand-edit generated files.

## Coordinates and the map

- Tile coordinates are signed `int32`, with a `z` plane on every position.
- The map is stored as **sparse chunks** keyed by `(chunkX, chunkY, z)`. A missing chunk is
  void: unwalkable and unrendered. This is what lets the map extend in any direction.
- Planes are independent 2D grids. Pathfinding never crosses `z`; movement between planes
  happens only via explicit objects (stairs, ladders).
- Movement is **4-directional**. No diagonals.
- Tiles carry a reserved 4-bit blocked-edge mask, currently always zero. Leave it alone
  unless implementing thin walls deliberately.

## Testing

Simulation tests build a world from fakes, step the manual clock, and assert exact state.
No sleeping, no database, no sockets. A 500-tick scenario should run in microseconds.

- Randomness is injected — combat and loot tests run under a fixed seed and assert exact
  outcomes, not statistical ranges.
- Assert against the recording `MessageSink`, not encoded bytes.
- `world/` ships a scripted client for protocol-level testing: a headless binary running a
  fixed intent sequence with assertions.

If a test needs `time.Sleep`, something is wrong with the design, not the test.

## Conventions

- Go standard formatting and idioms. `log/slog` for logging, injected, never the package
  default.
- Errors wrapped with context, not swallowed. Validation failures at boot are fatal —
  bad game data should stop startup, not surface as a nil dereference mid-session.
- Keep struct tags short on wire types; they are repeated in every frame.
- Comments explain *why*, not *what*.

## Content constraints

This is a public learning project with no affiliation to any existing game. See ASSETS.md
before adding art, item names or monster names — the short version is generic fantasy or
original only, and no assets or data from any other game.

## Scope

Deliberately out of scope for now: client auto-update, build version enforcement, PvP,
trading, banking, quests, anti-cheat, horizontal scaling. Don't add them speculatively.
